# 楽曲管理画面(`/tracks`)画面詳細設計

作成日: 2026-07-29
ステータス: 確定(ブレインストーミング済み・実装計画待ち)

## 1. 位置づけ

[楽曲管理機能 概要設計書](../../music-management-overview-design.md) の
4章で「画面の詳細設計は別途 `frontend-design` でのブレインストーミングにより
作成する」とされていた部分の詳細設計。データ層・API(`/api/tracks`・
`/api/tracks/:id`・`/api/audio-types`)は実装済みで、本書はその上に載る
`/tracks` 画面のレイアウト・操作フロー・エラー処理・テスト方針を定める。

対象範囲は概要設計書のスコープ(1章)をそのまま引き継ぐ。
`audio_types` マスタ自体の編集、`schedules.json` との連携は本書でも対象外。

## 2. 保存モデル

既存のスケジュール画面(`/`)は「編集モード + 明示的な保存ボタン」方式だが、
楽曲管理画面は**全操作を即時にサーバーへ反映する**方式とする。

理由: アップロード・削除は性質上その場でサーバーに反映するしかない操作であり、
名前変更・音声タイプ割り当てだけを「保存待ち」にすると、画面内で保存モデルが
2つ混在してしまう。すべて即時反映に揃えることで、行ごとに独立した CRUD 操作
という実態とUIの一貫性が取れる。

## 3. 画面構成・状態遷移

新規ルート `src/app/tracks/page.tsx`。

- `schedules.json` と異なり、`db/music.sqlite3` は常にバックエンド側の
  マイグレーションで存在している前提のため、`/` にある「初期化ダイアログ」
  フェーズ(`needs-init`)に相当するものは**不要**。
- 状態は `loading` → (`GET /api/tracks` と `GET /api/audio-types` を並行取得) →
  `ready`、取得失敗時は `load-error`。
- `load-error` の文言・見た目は `/` の実装(`src/app/page.tsx` の
  `phase === 'load-error'` 分岐)と同じものを踏襲する
  (「読み込みに失敗しました。ページを再読み込みしてください。」)。
- `/` の閲覧⇄編集モードのような二値状態は持たない。`ready` になった時点で
  常にすべての行が操作可能。

## 4. レイアウト

```
┌ 時報 設定                              [🕐][🎵] ┐  ← ヘッダー右にアイコン切替
├──────────────────────────────────────────────┤
│ 📁 .wav をドラッグ&ドロップ、またはクリックして追加  │  ← 常設ドロップゾーン
│                                                │
│ アップロード済み                                │
│  chime_intro          [D][ ][ ]           ✕   │
│  school_bell          [ ][N][ ]           ✕   │
│                                                │
│ 初期音源・その他(名前変更・削除不可)              │
│  default_chime        [D][ ][ ]           🔒   │
└──────────────────────────────────────────────┘
```

D/N/A はそれぞれ DEFAULT/NOTIFICATION/ALARM のトグルバッジ(複数選択可)。

### 4.1 ナビゲーション(ヘッダー)

`/` と `/tracks` を行き来する導線は、ヘッダー右端の🕐(スケジュール)/
🎵(楽曲管理)のアイコン2択セグメントで表現する。共有コンポーネント
`src/components/NavSwitcher.tsx` として実装し、両方の `page.tsx` の
ヘッダー内にそれぞれ組み込む(`RootLayout` 自体は変更しない。各画面が
自分のヘッダーを持つという既存構造をそのまま維持する)。

### 4.2 一覧の2セクション構成

一覧は次の2セクションに分ける。

| セクション見出し | 対象 `origin` | 可能な操作 |
| --- | --- | --- |
| アップロード済み | `user` | 名前変更・音声タイプ割り当て変更・削除 |
| 初期音源・その他(名前変更・削除不可) | `default`・`unknown` | 音声タイプ割り当て変更のみ |

**注記(概要設計書との整合)**: バックエンド設計上 `origin: "default"` と
`"unknown"` は全く同じ扱い(読み取り専用・タイプ変更のみ可)のため、UI上も
1セクションにまとめる。`unknown` は「想定外の `file_path` を持つ行」という
稀なフォールバックケースであり、`default` と見分けて表示する価値がないため、
セクション内で区別しない(ソートは名前順に両者を混在させる)。

各セクション内の行の並び順は名前の昇順とする。

## 5. コンポーネント構成

既存の `ConfirmDialog`・`ErrorDialog` は汎用コンポーネントのためそのまま再利用する。
新規追加分は以下。

| コンポーネント | 役割 |
| --- | --- |
| `src/app/tracks/page.tsx` | 画面本体。データ取得・状態管理・API 呼び出しの起点 |
| `src/components/NavSwitcher.tsx` | ヘッダー右の🕐/🎵アイコン切替(`/` にも組み込む) |
| `src/components/UploadDropzone.tsx` | 常設ドロップゾーン。1ファイルのみ受付 |
| `src/components/TrackSection.tsx` | 「アップロード済み」または「初期音源・その他」1セクション分の見出し+行リスト |
| `src/components/TrackRow.tsx` | 1行分。インライン名前編集・音声タイプバッジ・削除ボタン。`origin` に応じて名前編集・削除ボタンの活性/非活性を切り替える |

## 6. インタラクション詳細(すべて即時反映)

### 6.1 名前変更(`origin: "user"` の行のみ)

行の名前表示をクリックするとテキスト入力に切り替わる。`Enter` キーまたは
フォーカスアウトで、値が変わっていれば `PATCH /api/tracks/:id` を実行する
(値が変わっていなければ何もしない)。`PATCH` は `name`・`audioTypeIds` を
両方必須とする全置換方式のため(6.2節参照)、この操作でも `audioTypeIds` は
その行の現在の割り当てのまま変更せずに送る。保存中は入力欄を無効化する。
失敗時は表示を元の名前に戻し、`ErrorDialog` でエラーを表示する。
`origin` が `default`/`unknown` の行は名前がクリック不可(そもそも
テキストではなく通常のラベルとして表示する)。

### 6.2 音声タイプ割り当て変更(全行で可能)

バッジをクリックすると、その行の現在の `audioTypeIds` に対してクリックした
タイプの ON/OFF を反転させた配列を計算し、即座に `PATCH` を実行する。
`PATCH` は `name`・`audioTypeIds` を両方必須とする全置換方式のため
(`src/app/api/tracks/[id]/route.ts`)、この操作でも `name` は現在の値のまま
変更せずに送る。保存中はその行のバッジ操作を無効化する。**楽観的更新は行わない**
(クリック時点では表示を変えず、サーバーからの応答で確定させる)。
理由: `/` 画面同様、失敗時のロールバック処理を持たずシンプルに保つため。
失敗時は `ErrorDialog` を表示する(表示は変わっていないため巻き戻し不要)。

### 6.3 削除(`origin: "user"` の行のみ)

`✕` ボタンクリックで既存の `ConfirmDialog` を表示する
(タイトル「◯◯を削除」、メッセージ「この操作は取り消せません。よろしいですか?」、
アクションラベル「削除する」)。確認後 `DELETE /api/tracks/:id` を実行し、
成功時は一覧からその行をローカルに除去する(再取得はしない)。
失敗時は `ErrorDialog` を表示する。`origin` が `default`/`unknown` の行は
削除ボタンの代わりに 🔒 アイコンを表示し、操作自体を提供しない。

### 6.4 アップロード

常設ドロップゾーンへのドラッグ&ドロップ、またはクリックによるファイル選択で
受け付ける。

- **クライアント側の事前チェック**(サーバー側と同じ制約をクライアントでも
  先にチェックし、即座にエラー表示することで往復を減らす): 拡張子が `.wav`
  であること、サイズが 10MB 以下であること。
- **複数ファイル同時ドロップへの対応**: 1ファイルのみ対応とする。複数の
  `.wav` が同時にドロップされた場合は何もアップロードせず、
  「一度に1つのファイルだけ選択してください」というエラーを表示する
  (バックエンド API `POST /api/tracks` が1ファイルずつの `multipart/form-data`
  を前提としており、キュー処理による順次アップロードは本フェーズのスコープ外)。
- 事前チェック通過後、`audioTypeIds` を空(`[]`)にした状態で
  `POST /api/tracks` を実行する。表示名はサーバー側でファイル名から
  自動生成されるため、クライアント側で名前を入力させる UI は持たない
  (概要設計書 7章の確定事項どおり)。
- アップロード中はドロップゾーンを無効化し、「アップロード中...」の表示に
  切り替える。
- 成功時は返却された楽曲を「アップロード済み」セクションに追加する
  (ローカルに `state` を更新。再取得はしない)。
- 失敗時(拡張子/サイズ/重複/バリデーションエラー含む)は `ErrorDialog` を
  表示する。

## 7. エラー処理まとめ

| 操作 | 失敗時の挙動 |
| --- | --- |
| 初回読み込み(`GET /api/tracks`・`GET /api/audio-types`) | `load-error` フェーズ表示 |
| 名前変更 (`PATCH`) | 表示を元の名前に戻し `ErrorDialog` |
| タイプ割り当て変更 (`PATCH`) | 表示は変えず `ErrorDialog`(楽観的更新をしていないため) |
| 削除 (`DELETE`) | 一覧はそのまま残し `ErrorDialog` |
| アップロード (`POST`、クライアント側事前チェック含む) | ドロップゾーンをアップロード前の状態に戻し `ErrorDialog` |

すべて既存の `ErrorDialog` コンポーネントをそのまま再利用する
(モーダルでエラー内容を表示し、OK で閉じる)。

## 8. テスト方針

既存の3層ピラミッド([テスト設計書](../../schedule-ui-testing-design.md)・
[楽曲管理機能 概要設計書](../../music-management-overview-design.md) 6章)を
そのまま踏襲する。API 層のテスト(`route.test.ts` 群)は実装済みで変更不要。

| レイヤー | 対象 | 主な確認内容 |
| --- | --- | --- |
| コンポーネント(Vitest + RTL) | `TrackRow` | インライン名前編集の開始/確定/キャンセル、バッジのON/OFF切り替えと`origin`による活性/非活性、削除ボタンの`origin`による表示切り替え |
| コンポーネント(Vitest + RTL) | `UploadDropzone` | 拡張子/サイズのクライアント側事前チェック、複数ファイルドロップ時のエラー表示、アップロード中の無効化表示 |
| コンポーネント(Vitest + RTL) | `NavSwitcher` | 現在ルートに応じたアクティブ表示、クリック時の遷移 |
| コンポーネント(Vitest + RTL) | `src/app/tracks/page.tsx` | `loading`/`ready`/`load-error` の状態遷移、各操作成功時のローカル状態更新、各操作失敗時の`ErrorDialog`表示 |
| E2E(Playwright) | 楽曲管理の主要シナリオ1本 | アップロード→一覧に反映→タイプ変更→削除、を一連で確認(概要設計書6章で既に決定済み。ユニット/APIで担保できる細かい分岐は重複させない) |

## 9. 本書のスコープ外

- 複数ファイル同時アップロードのキュー処理(6.4節で明示的に見送り)
- `audio_types` マスタ自体の追加・編集
- `schedules.json`(`minute_settings`)との連携
